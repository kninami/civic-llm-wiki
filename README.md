# 시민사회 자동화 도구 위키

시민사회단체가 각자 만든 **자동화 도구**를 모아, 다른 단체가 보고 **자기 조직에 옮겨 심을 수 있게** 하는 위키입니다.
도구 하나마다 "무엇을 왜 만들었나 · 어떻게 작동하나 · 우리 단체에 어떻게 옮기나 · 어떤 위험이 있나"가 한 파일에 들어 있습니다.

이 위키는 AI 활용을 권장하지 않습니다. 원본 가이드가 명시한 입장이며, **"쓰지 않는 선택"도 정당한 결론**으로 남겨둡니다.
자세한 원칙은 [wiki/guardrails.md](wiki/guardrails.md)를 보세요.

---

## 1. LLM 위키란 무엇이고, 어떻게 쓰나

### 기존 방식과 무엇이 다른가

보통 AI에게 문서를 물어볼 때는 파일 몇 개를 올리고 질문합니다. AI는 그때그때 문서를 훑어 답을 만들고, 대화창을 닫으면 그 이해는 사라집니다. 다음에 물으면 처음부터 다시 읽습니다.

이 위키는 반대입니다. **AI가 원본을 읽고 정리해서 위키 문서로 미리 써 둡니다.** 도구가 하나 들어올 때마다 도구 페이지를 쓰고, 새 용어가 나오면 개념 페이지를 만들고, 관련 페이지끼리 링크를 걸고, 목록과 기록을 갱신합니다. 그래서 질문할 때는 이미 정리된 위키를 근거로 답이 나옵니다. 자료가 쌓일수록 위키가 두꺼워집니다.

**사람은 자료를 모으고 질문을 던지고, 위키 본문은 AI가 씁니다.**

### 폴더 세 개의 역할

```
civic-ai-guideline/
├── AGENT.md    ← AI에게 주는 규칙서. "이 위키를 어떻게 쓰고 유지하라"
├── raw/        ← 원본. PDF, 코드, 회의록 등 받은 그대로. AI는 읽기만 하고 절대 고치지 않는다
└── wiki/       ← AI가 쓰고 유지하는 본문
    ├── index.md       카탈로그. 질문에 답하기 전 AI가 먼저 읽는 파일
    ├── log.md         시간순 작업 기록
    ├── guardrails.md  AI 활용 원칙과 주의사항
    ├── tools/         도구 1개 = 파일 1개
    └── concepts/      용어사전. 활동가 눈높이로 한 개념 = 한 파일
```

### 쓰는 법 — 폴더를 열고, 거기서 물어본다

이 위키는 **폴더 하나가 곧 하나의 대화 상대**입니다. 특별한 서버나 설치가 필요 없습니다.

1. **이 폴더를 내 컴퓨터에 받는다** (→ [2번](#2-내-컴퓨터에-가져오기))
2. **그 폴더에서 AI 에이전트를 켠다** — Claude Code, Codex, Gemini CLI 등 폴더의 파일을 읽고 쓸 수 있는 도구면 됩니다. 터미널에서 그 폴더로 이동한 뒤 실행하면 됩니다.

   ```bash
   cd civic-ai-guideline
   claude          # 또는 codex, gemini 등
   ```

3. **처음 한 번은 규칙서를 읽히고 시작한다**

   > AGENT.md를 읽고 이 위키의 규칙에 따라 답해줘.

   에이전트에 따라 자동으로 읽는 파일 이름이 다릅니다(Claude Code는 `CLAUDE.md`, Codex는 `AGENTS.md`). 위 문장을 먼저 말해주는 게 가장 확실합니다. 자주 쓴다면 자기 도구가 읽는 이름으로 링크를 걸어두면 편합니다.

   ```bash
   ln -s AGENT.md CLAUDE.md      # Claude Code를 쓰는 경우
   ```

4. **그냥 물어본다.** AI가 `wiki/index.md`를 먼저 읽고 관련 페이지를 찾아 답합니다.

**질문 예시**

- "회원 주소록에 우편번호를 채우고 싶은데 쓸 만한 도구가 있나?"
- "우편번호 자동검색 도구를 우리 단체에 옮겨 심으려면 뭐부터 해야 하나? 얼마나 걸리나?"
- "뉴스레터 초안을 생성형 AI로 쓰려고 하는데, 우리 조직에서 먼저 정해야 할 게 뭔가?"
- "위키에 있는 도구 중에 개인정보가 외부로 나가는 것들만 모아서 보여줘."
- "웹 스크래핑이 뭔지 코딩 모르는 사람 기준으로 설명해줘."

**답이 나올 때 눈여겨볼 것**

- AI는 근거가 된 페이지를 `[[페이지이름]]`으로 인용합니다. 그 파일을 직접 열어 확인하세요.
- 위키에 없는 내용은 **"위키에 없음"이라고 말하도록** 규칙에 정해두었습니다. 그런 답이 나오면 그건 실패가 아니라 정상입니다. 채워야 할 자리를 찾은 겁니다.
- "X를 자동화하고 싶다"는 질문에는 주의사항 검토가 답에 함께 나옵니다. 특히 **생성형 AI 없이 되는 일이면 그쪽을 권합니다.**

### 눈으로 보며 쓰기 (선택)

위키 문서들은 `[[대괄호 두 개]]`로 서로 링크되어 있습니다. [Obsidian](https://obsidian.md)에서 이 폴더를 열면 링크를 따라다니며 읽고, 그래프로 전체 연결을 볼 수 있습니다. **한쪽에 Obsidian, 한쪽에 AI 에이전트**를 띄워두고 — AI가 고치는 걸 실시간으로 보며 쓰는 방식을 권합니다.

Obsidian 없이 그냥 텍스트 편집기나 GitHub 웹에서 읽어도 아무 문제 없습니다.

## 2. 내 컴퓨터에 가져오기

두 가지 방법이 있습니다. **나중에 도구를 보태거나 최신 내용을 계속 받아볼 생각이면 A**, 일단 한 번 보기만 할 거면 B를 쓰세요.

### A. git으로 받기 (권장)

git이 설치되어 있어야 합니다. (Mac은 터미널에서 `git --version`을 쳐보면 없을 때 설치를 안내합니다.)

```bash
cd ~/Documents                                             # 받고 싶은 위치로 이동
git clone https://github.com/kninami/civic-llm-wiki.git
cd civic-llm-wiki
```

나중에 **최신 내용을 받을 때:**

```bash
git pull
```

이 방식의 장점은 남들이 새로 등재한 도구를 `git pull` 한 번으로 받을 수 있고, 내가 만든 도구를 다시 돌려보낼 수 있다는 것입니다.

### B. 파일로 내려받기 (git 없이)

1. https://github.com/kninami/civic-llm-wiki 접속
2. 초록색 **`Code`** 버튼 → **`Download ZIP`**
3. 내려받은 zip 파일의 압축을 풀고, 원하는 위치에 둔다

또는 터미널에서 한 줄로:

```bash
curl -L -o civic-wiki.zip https://github.com/kninami/civic-llm-wiki/archive/refs/heads/main.zip
unzip civic-wiki.zip
```

이 방식은 간단하지만 **업데이트를 받으려면 매번 다시 내려받아야 합니다.** 내가 고친 내용을 되돌려 보내기도 어렵습니다.

### 어느 쪽이든, 받은 다음

폴더 안에 `AGENT.md`, `raw/`, `wiki/`가 있으면 정상입니다. 이제 그 폴더에서 [1번의 사용법](#쓰는-법--폴더를-열고-거기서-물어본다)대로 질문하면 됩니다.

## 3. 내가 만든 자동화 도구 추가하기

**위키 본문은 사람이 쓰지 않습니다.** 여러분은 원본을 폴더에 넣고 대화를 나눌 뿐이고, 페이지는 AI가 규격에 맞춰 씁니다. 도구 페이지를 직접 손으로 쓰려고 애쓰지 마세요.

### 넣기 전에 반드시 — 개인정보·비밀키 확인

원본을 `raw/`에 넣기 전에 **직접 눈으로** 확인하세요. AI도 등재 전에 한 번 더 검사하지만, 사람이 먼저 보는 게 원칙입니다.

- API 키, 토큰, 비밀번호, `.env` 파일, 서비스 계정 키 파일
- 실명·연락처·주소가 든 샘플 데이터, 회원·후원자 명부
- 회의록, 인터뷰 녹취, 회계 자료
- 스크린샷 속에 딸려 들어간 개인정보

키가 들어 있다면 **지우기 전에 먼저 그 키를 폐기(재발급)하세요.** 파일에서 지워도 이미 유출된 키는 유효합니다.

### 단계

**1) 원본을 `raw/`에 그대로 넣는다**

코드, 스크립트, 사용 설명, 스크린샷, 관련 회의록 — 정리하지 말고 **받은 그대로** 넣으세요. 정리는 AI가 합니다. `raw/`는 원본 보관소라 AI가 절대 고치지 않습니다.

**2) 그 폴더에서 AI 에이전트를 켜고 등재를 요청한다**

> AGENT.md를 읽고, raw/에 새로 넣은 `<파일명>`을 도구로 등재해줘.

**3) AI의 질문에 답한다** — 여기가 제일 중요합니다

AI는 코드만 보고는 알 수 없는 것들을 물어봅니다. 성의껏 답할수록 다른 단체가 옮겨 심기 쉬워집니다.

- 어떤 반복 노동을 없애려고 만들었나. 만들기 전에는 어떻게 했나
- 누가, 얼마나 자주 쓰나. 실제로 뭐가 달라졌나
- **이 도구의 가장 위험한 지점이 뭔가** (AI가 반드시 묻습니다)
- 만들면서 어디서 막혔나. 사고나 실패는 없었나
- 사람이 중간에 확인하고 개입하는 지점이 있나

**4) AI가 쓴 결과를 검토한다**

AI는 다음을 만들거나 고칩니다.

| 파일 | 무엇이 |
|---|---|
| `wiki/tools/<도구>.md` | 도구 페이지 (개요·개념·작동방식·코드·사용법·주의사항·사례) |
| `wiki/concepts/<개념>.md` | 새 용어가 나왔다면 개념 페이지 |
| `wiki/index.md` | 도구 표에 한 줄 추가 |
| `wiki/log.md` | 맨 위에 등재 기록 추가 |

직접 열어서 확인하세요. 특히:

- **작동 방식**이 실제와 맞나. 사람이 개입하는 지점이 제대로 적혔나
- **주의사항 표**의 "남은 위험" 칸이 비어 있지 않나
- 추정으로 쓴 부분에 `> [추정]` 표시가 붙어 있나. 사실과 다르면 알려주고 고치게 하세요
- 개인정보나 키가 본문으로 옮겨오지 않았나

**5) 다시 돌려보낸다**

git으로 받았다면:

```bash
git checkout -b add-우리단체-도구이름
git add raw/ wiki/
git commit -m "등재: <도구 이름> (<단체명>)"
git push -u origin add-우리단체-도구이름
```

푸시 후 GitHub에 뜨는 안내를 따라 Pull Request를 만들면 됩니다. 저장소에 푸시 권한이 없으면 GitHub에서 **Fork**를 먼저 뜨거나, 파일을 그대로 담당자에게 전달해도 됩니다.

파일로 내려받아 쓰고 있다면 `wiki/tools/`의 새 파일과 `raw/`의 원본을 담당자에게 보내면 됩니다.

### 어떤 도구를 넣으면 좋은가

- **AI를 안 쓴 자동화도 환영합니다.** 오히려 권장합니다. 스프레드시트 수식, 간단한 스크립트, 매크로 모두 좋습니다. 생성형 AI 없이 되는 일은 그쪽이 낫다는 게 이 위키의 입장입니다.
- **완성되지 않아도 됩니다.** `아이디어` · `시범` · `운영중` · `중단` 중 어느 상태든 등재할 수 있습니다.
- **실패담이 특히 값집니다.** 중단한 도구, 잘 안 된 이식 기록은 지우지 않습니다. 왜 안 됐는지가 다음 단체를 구합니다.
